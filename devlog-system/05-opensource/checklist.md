# 05 · 工具站开源化清单

> 决定：整个站点开源，不担心被复制。
> 这份文档解决两件事：**开源前必须清理什么**（真实风险），**开源后怎么拿到最大收益**。

---

## 一、为什么"不怕复制"这个判断是成立的

纯前端工具站的真壁垒**从来不是代码**，而是这些无法被 fork 的东西：

| 资产 | 能否被复制 |
|---|---|
| 9 个月积累的搜索收录 | ❌ 复制者从零开始 |
| 域名权重与外链 | ❌ 无法迁移 |
| 已上线的场景页面矩阵 | ❌ 需要时间和判断 |
| 广告位的收益关系 | ❌ 账号是新开的 |
| 品牌认知 | ❌ |

代码被 fork，复制者拿到的是一个**没有流量、没有权重、没有收录**的空壳。
他还要自己再走一遍你走过的 9 个月。

**所以开源的成本比想象中低，收益比想象中高。**

---

## 二、但有一件事不能放：品牌

**代码可以复制，名字不行。**

如果品牌资产（名称、Logo、UI 视觉）也一并放开，别人可以做一个
"和你一模一样、连名字都一样"的站点——那时用户分不清谁是官方，
你的流量和口碑会被稀释，甚至被劣质副本反噬。

### 具体做法

1. **代码用开源协议，品牌资产单独声明**
   在 LICENSE 之外加一份 `TRADEMARK.md`：
   > 本项目代码遵循 Apache-2.0 协议。
   > 但项目名称、Logo、品牌视觉不在授权范围内。
   > 禁止使用本项目品牌名义部署衍生站点或提供服务。

2. **站点内加"官方身份"标识**
   页脚或关于页明确写：这是官方部署实例，源码地址是 xxx。
   让用户能分辨。

---

## 三、许可证怎么选

| 协议 | 特点 | 适配度 |
|---|---|---|
| **Apache-2.0** ⭐ | 宽松 + 明确不授予商标权 + 含专利授权 | **推荐** |
| MIT | 最宽松，但商标条款不明确 | 次选 |
| AGPL | 要求网络服务也开源 | 对纯前端约束力弱，且劝退商业采用 |
| Commons Clause / Elastic | 限制商业提供服务 | 失去 OSI 认证，影响社区接受度 |

**推荐 Apache-2.0**，理由很实际：
它的第 6 条明确写明**不授予商标许可**，
正好对应上面第二节"品牌不放开"的需求。MIT 没有这个明确条款。

### 关于"防止别人换个广告位部署"

说实话，**协议层面很难完全阻止**。
Apache-2.0 允许他人部署并商业化，只要保留署名和不用你的品牌。

如果你确实想限制，只能走 Commons Clause 这类，
但代价是社区接受度大幅下降、拿不到外部贡献。

建议接受这一点——按第一节的判断，他们竞争不过你已有的沉淀。
**把精力放在"官方站点体验更好、场景覆盖更全"上，比在协议上设防更有效。**

## 四、开源前必须做的清理（真实风险）

这一节最重要。仓库一旦公开，历史提交里的东西都能被翻出来。

### 必查清单

- [ ] **`.env` 和所有环境配置文件**（确认已在 `.gitignore`）
- [ ] **API key / token / secret**（搜索 `key`、`token`、`secret`、`api_`、`Bearer`）
- [ ] **广告 ID**（Google AdSense client ID、其他广告平台的 publisher ID）
- [ ] **分析 ID**（GA measurement ID、其他统计服务的站点 ID）
- [ ] **私有域名 / 内部地址**
- [ ] **Cloudflare Workers 的任何密钥或绑定配置**
- [ ] **第三方服务的私有凭证**（图床、CDN、对象存储）
- [ ] **数据库 / D1 的连接信息**

### 关键：检查 Git 历史

仅仅删除当前文件**不够**——历史提交里仍可能包含。

```bash
# 搜索历史中的敏感词
git log -p | grep -iE "api[_-]?key|secret|token|password|Bearer" | head -50
```

如果发现泄露：
1. **先轮换密钥**（把泄露的 key 全部作废换新的）
2. 再用 `git filter-repo` 清理历史
3. 强制推送

**顺序不能反**——先轮换再清理，因为清理前泄露已经发生。

### 改造建议

把所有配置改为环境变量，并提供 `.env.example`：

```bash
# .env.example
NUXT_PUBLIC_SITE_URL=https://example.com
NUXT_PUBLIC_ADSENSE_CLIENT=ca-pub-xxxxxxxxx
NUXT_PUBLIC_GA_ID=G-XXXXXXX
# 以下为私有，不提交
# API_SECRET=xxx
```

README 里说明：部署自己的实例需要自己申请广告 ID 和分析 ID。

## 五、开源后的收益设计

开源不会自动带来流量。要主动设计回流路径。

### 1. README（第一屏最重要）

```markdown
# 项目名

一句话说明它解决什么问题。

🔒 **所有处理都在浏览器本地完成，数据不上传服务器。**
🚀 在线体验：<官方站点链接>

## 为什么开源
（说明隐私主张可被审计——这是纯前端工具最大的差异化）

## 快速开始
...
```

**前两屏就要有站点链接**，不要埋在文档底部。

### 2. npm 包（如果是组件库形态）

`package.json` 里：
```json
{
  "homepage": "https://官方站点",
  "repository": { "type": "git", "url": "..." },
  "keywords": ["..."]
}
```

包内**不要塞硬广**（控制台打印链接那种），会引起反感。

### 3. 文档站 = SEO 页

组件库的文档页天然是精准的开发者意图页面。
每个组件的文档页都要能独立被搜到。

### 4. 版本发布 = 内容素材

每次 release 都是一篇博客素材——正好喂给 DevLog System：
- 做了什么、为什么做
- 踩了什么坑
- 数据变化（体积、性能）

## 六、风险提醒：恶意副本

开源后可能出现**伪装成你的站点**的副本：
- 换个相似域名
- 界面一模一样
- 但植入了数据上传或恶意脚本

这会直接损害你的声誉，尤其是你的核心卖点是"数据不上传"。

### 应对

1. README 和站点显眼位置声明：
   > 唯一官方站点是 xxx，其他任何域名均非官方。

2. 站点首页加一个可验证标识（如固定的官方声明区块）

3. 定期搜索一下有没有仿冒域名

4. 如果发现，可通过域名注册商或托管平台投诉

## 七、执行 Checklist

### 开源前

- [ ] 全库搜索敏感词，清理 API key / 广告 ID / 分析 ID
- [ ] 检查 Git 历史，必要时先轮换密钥再清理历史
- [ ] 配置改为环境变量，提供 `.env.example`
- [ ] 确定许可证（建议 Apache-2.0）
- [ ] 写 `TRADEMARK.md`（品牌不放开）
- [ ] 写 README（前两屏含站点链接 + 隐私主张）
- [ ] 写 `CONTRIBUTING.md`（降低贡献门槛）
- [ ] 确认第三方依赖的许可证兼容

### 开源后

- [ ] README 明确官方站点身份
- [ ] 站点页脚加"官方部署实例"声明
- [ ] 提交到相关 awesome 列表 / 开发者社区
- [ ] 每次 release 同步产出一篇内容（喂给 DevLog）
- [ ] 定期巡查仿冒域名

---

## 八、和 DevLog System 的关系

这个开源项目是内容体系的**最佳载体**：

- 它的开发过程 → 日志 → 博客文章
- 它的 README / 文档站 → 开发者受众，与博客受众重合
- 它的组件库 → 博客里"可运行 Demo"的载体
- 它的 release → 持续的内容素材

之前那套内容体系，终于有了一个具体的产品来承接。
