# 00 · 内容策略：三层内容模型

---

## 一、为什么必须分层

过程记录（"今天改了什么、报了什么错"）**不能直接当博客文章发**。

- 流水账没有检索价值，AI 也能编
- 读者不关心你今天做了什么，只关心"我遇到这类问题怎么解决"
- 单条记录太薄，撑不起一篇

所以过程记录是**原料**，不是成品。必须经过分层升级。

---

## 二、三层模型

| 层 | 形态 | 产出成本 | 主要价值 | 发布平台 |
|---|---|---|---|---|
| **L0 日志** | 结构化条目 | 0（自动） | 素材池，不对外 | `.dev-log/log.md` |
| **L1 碎片** | 单条日志展开 | ~5 分钟 | 活跃度 + **选题验证** | X / dev.to |
| **L2 文章** | 3–5 条日志聚合 | 30–60 分钟 | SEO 沉淀 + 域名权重 | 自己的博客 |

### L1 的真正价值不是流量

X 上内容生命周期只有几小时，dev.to 稍长但也有限。**指望它们带来持续流量不现实。**

L1 的真正作用是**低成本选题测试**：
哪条碎片反响好 → 说明这个话题有人关心 → 扩写成 L2。
等于用 5 分钟的碎片，提前验证 1 小时的投入值不值。

---

## 三、什么时候升级为 L2

**不按时间升级（"攒了一周就写一篇"），按信号升级。**

满足任一即可：

1. **同主题攒够 3–5 条日志**
   例：连着几天跟 Cloudflare D1 事务限制搏斗 → 《Cloudflare D1 实战踩坑》

2. **一个完整阶段结束**
   功能上线、项目完成、迁移收尾 —— 天然就是阶段性总结

3. **某个坑花了很久**
   同一问题上耗超过 1 小时 → 说明它值得写

4. **有真实数据**
   成本、性能、耗时 —— 有数字就能撑起一篇

### 不值得升 L2 的

- 单个小报错
- 纯配置调整
- 无结论的探索过程
- 只有"我做了 X"，没有结果和判断

---

## 四、L2 的聚合方式

**不是把日志按时间罗列，而是围绕主题重新组织。**

```
L0：散布在一周里的 5 条 D1 相关记录
        ↓
按「问题类型」分组，而非时间顺序
        ↓
L2 结构：
   1. 背景：我这次要做什么
   2. 主体：按主题分组的踩坑记录
   3. 数据：真实结果（性能 / 成本 / 耗时）
   4. 总结：如果重做会改什么
```

**核心区别**：
- L1 = "今天遇到了 X"（一次性）
- L2 = "做这类事情会遇到 A / B / C"（长期检索价值）

## 五、博客文章的内容公式

> ⚠️ **本节已废弃为文章骨架，见 `07-article-archetypes.md`。**
> 该公式被严格套用后，19 篇文章长成同一个八槽位表单
> （`## TL;DR` 19/19、`## Lessons Learned` 16/19），
> 既造成模板化，也让 TL;DR 主动喂养 AI Overview。
> 本节仅保留为**写完后的自检清单**，不得当作骨架去填。

每篇固定这个骨架，写起来快，质量也稳定：

```markdown
1. 我做了什么（一句话 + 成品链接/截图）
2. 为什么做（真实动机，不是"因为技术好玩"）
3. 技术路径（具体选型和理由）
4. 真实数据（成本、耗时、性能、用户数——哪怕很小）
5. 踩过的坑（至少 2 条，越具体越好）
6. 如果重做我会改什么
```

**第 4、5 段是全部价值来源**，也是 AI 无法替代的部分。

## 六、选题方向（贴合前端 / 全栈 + 独立开发者可做）

### 关键筛选标准

不是"选题小"，而是**有真实结果**。

| 低价值（避开） | 高价值（推荐） |
|---|---|
| 一个人可以做的 10 个项目 | 我做了个 XX，上线 3 个月，真实账单 $0.4 |
| 独立开发者如何时间管理 | 小工具从 0 到第一个付费用户，改了这 5 处 |
| Nuxt 搭建博客教程 | 把 XX 从 Vercel 迁到 Cloudflare，前后对比数据 |

低价值那类：饱和、AI 能生成、吸引的是"想做但没做"的人。

### 四个推荐类型

1. **成本实录型** —— Cloudflare 免费额度到底能撑多大流量（跑真实数据）
2. **迁移实录型** —— 从 X 迁到 Y，前后对比数据
3. **小工具构建型** —— 一个周末做完的小工具，完整过程 + 源码
4. **踩坑解决型** —— 某个具体问题（SSR / 边缘函数 / 文件上传）的真实解决过程

共同点：**都有可验证的结果**，不是纯教程。

### 按时记录习惯

做项目时随手记这几项（Skill 会自动做，但你可能想手动补充）：

- 用的库 / 服务名
- 为什么选它（当时对比过什么）
- 接入花了多久
- 踩的坑（报错原文 + 怎么解决的）
- 用了多久后的感受变化

一篇小项目通常用到 5–10 个工具。写 10 篇项目记录，
手里就有 100+ 条真实使用清单 —— **这是将来工具专区第一批内容的原材料。**

## 七、发布注意事项

### dev.to 的重复内容问题

如果先在 dev.to 发完整文章再搬到自己博客，Google 可能判定你的博客是抄袭方
（dev.to 域名权重更高）。

**二选一处理：**
- dev.to 只发**摘要 + 链接**回自己博客（推荐）
- 或全文发，但设置 `canonical URL` 指向自己的博客（dev.to 支持该字段）

### X 的碎片不要浪费

一条一条发太碎。攒够 5–7 条同主题的做成 **thread**，
效果比单条好很多，而且 thread 稍作扩充就能变成 L2 初稿。

## 八、产出节奏

**不定"每周一篇"的硬指标，按信号走。**

```
日常：L0 持续自动积累（零成本）
随时：挑有价值的发 L1（5 分钟）
信号出现：攒够 3–5 条同主题 → 写 L2（30–60 分钟）
```

按正常编码节奏，大概 **2–3 周出一篇 L2**。频率可持续，也不占太多时间。
