# 03 · L1 碎片：日志 → X / dev.to

---

## 一、L1 的定位

**L1 的真正价值不是流量，是验证。**

X 上内容生命周期只有几小时，dev.to 稍长但也有限。
指望它们带来持续流量不现实。

L1 的作用是**低成本选题测试**：
哪条碎片反响好 → 说明这个话题有人关心 → 扩写成 L2。

等于用 5 分钟的碎片，提前验证 1 小时的投入值不值。

---

## 二、什么样的日志值得发 L1

| 值得发 | 不值得发 |
|---|---|
| 有报错原文 | 只是"改了个 bug" |
| 有反直觉的发现 | 常规操作 |
| 有具体数字 | 没有数据 |
| 一个限制/坑 | 配置调整 |
| 一个对比决策 | 无结论的探索 |

简单判断：**别人看到会不会"哦？"一下。**

## 三、X 的写法

### 单条

```
踩了个坑：Cloudflare D1 的事务不支持跨 HTTP 请求，
只能在单次 Worker 调用内完成。

想做批量写入就得改用 batch API，
不然重试逻辑的边界情况能写到你怀疑人生。

#cloudflare #d1
```

### Thread（推荐）

**一条一条发太碎。攒够 5–7 条同主题的做成 thread。**

```
1/ 上周给项目加图片优化，踩了 @nuxt/image 三个坑，
   记录一下，免得下次又踩。

2/ 第一个：SSR 下 useImage() 返回 undefined
   ...

3/ 第二个：lazy 加载会让 LCP 变差
   ...

4/ 第三个：purge 配置漏了动态类名
   ...

5/ 完整记录和截图整理成文章了：
   <链接>
```

**Thread 的好处**：
- 效果比单条好很多
- 稍作扩充就能变成 L2 初稿

---

## 四、dev.to 的写法

### 重复内容问题（必须处理）

如果先在 dev.to 发完整文章再搬到自己博客，
Google 可能判定你的博客是抄袭方（dev.to 域名权重更高）。

**二选一：**

| 方案 | 做法 | 适用 |
|---|---|---|
| **摘要 + 链接**（推荐） | dev.to 只发要点，末尾链回自己博客 | 博客已有该文 |
| **canonical URL** | 全文发，但设置 canonical 指向自己博客 | 想利用 dev.to 流量 |

dev.to 支持在 frontmatter 设置 canonical：

```yaml
---
title: "..."
canonical_url: https://your-blog.com/posts/xxx
---
```

### dev.to 内容形态

比 X 长，比 L2 短。适合：
- 单个坑的完整记录（500–1000 字）
- 一个小技巧
- 一次迁移的简要过程

## 五、L0 → L1 的转换方式

三种模式，可选（详见 `04-build/mvp-scope.md`）：

| 模式 | 做法 | 成本 |
|---|---|---|
| **A：自动展开** | Skill 把单条日志扩写成可发文本 | 你改改就发 |
| **B：只列素材** | Skill 整理成要点，你自己组织语言 | 你写 |
| **C：混合** | 技术类自动展开，主观判断类列素材 | 折中 |

**第一版建议用 B**（只列素材）—— 先把素材池攒起来，
转换方式等实际用起来再定，避免过早优化。

---

## 六、发布频率

不用定硬指标。**看到有料的就发，没有就不发。**

```
日常：L0 自动积累
有料时：5 分钟发一条 L1
反响好：扩写成 L2
```

一周发 2–3 条 L1 是舒适节奏，不影响编码。
