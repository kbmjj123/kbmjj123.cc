# 03 · L2 文章：日志聚合 → 博客

---

## 一、什么时候升级为 L2

**不按时间升级，按信号升级。** 满足任一即可：

| 信号 | 说明 | 例子 |
|---|---|---|
| 同主题攒够 3–5 条 | 标签高度重合 | 连着几天跟 D1 事务搏斗 → 《Cloudflare D1 实战踩坑》 |
| 一个完整阶段结束 | 功能上线 / 项目完成 / 迁移收尾 | 《把项目从 Vercel 迁到 Cloudflare 的全过程》 |
| 某个坑花了很久 | 同一问题耗时 > 1 小时 | 《一个 hydration 问题排查了两小时》 |
| 有真实数据 | 成本 / 性能 / 耗时 | 《Cloudflare 免费额度到底能撑多大流量》 |

### 不值得升 L2 的

- 单个小报错
- 纯配置调整
- 无结论的探索过程
- 只有"我做了 X"，没有结果和判断

---

## 二、聚合的核心原则

**不是把日志按时间罗列，而是围绕主题重新组织。**

```
L0：散布在一周里的 5 条 D1 相关记录
        ↓
按「问题类型」分组，而非时间顺序
        ↓
L2 成品
```

### 核心区别

| | 内容 | 价值 |
|---|---|---|
| L1 | "今天遇到了 X" | 一次性 |
| L2 | "做这类事情会遇到 A/B/C" | 长期检索价值 |

---

## 三、L2 文章结构

```markdown
1. 我做了什么（一句话 + 成品链接/截图）
2. 为什么做（真实动机）
3. 技术路径（具体选型和理由）
4. 主体：按主题分组的踩坑记录 ← 日志聚合而来
5. 真实数据（成本、耗时、性能）
6. 如果重做我会改什么
```

**第 5、6 段是 AI 无法替代的部分**，必须你亲自补。

---

## 四、聚合指令

对 Agent 说：

```
生成博客草稿
```

或指定范围：

```
整理一下最近关于 cloudflare 的记录
把 ~/proj-a 和 ~/proj-b 里 d1 相关的记录聚合一下
```

## 五、执行步骤（Skill 内部）

```
1. 读取 .dev-log/log.md
        ↓
2. 按标签分组，找关联度高的 3–5 条
        ↓
3. 列出孤儿素材让用户认领
   （未配图的条目、未归属的截图）
        ↓
4. 生成草稿到 .dev-log/drafts/YYYY-MM-DD-<主题>.md
        ↓
5. 询问是否标记已用条目为 used
```

### 孤儿素材必须先处理

```
以下素材还没归属，要不要用？
1. shots/2026-10-17-143245.png —— 猜是 SSR 报错截图？
2. shots/2026-10-17-160812.png —— 猜是部署成功页面？

以下条目标注了建议配图但没有：
1. [14:32] hydration 后布局错位
```

你点一下就归位，比事后翻文件夹找图省力太多。

## 六、草稿生成后你要做的

**Skill 只产出初稿，发布前必须你过一遍：**

- [ ] 补充主观感受（"这个坑烦了我两小时"）
- [ ] 补充最终效果（真的解决了吗？）
- [ ] 检查是否有敏感信息残留
- [ ] 确认截图都放对位置
- [ ] 改标题（Skill 给的多半太直白）
- [ ] 检查数据准确性

**预算 30–60 分钟。**

---

## 七、标题

Skill 生成的标题多半太工程化（"D1 事务限制与 batch API 使用"）。

**你要改成读者视角：**

| Skill 给的 | 你改成 |
|---|---|
| D1 事务限制与 batch API 使用 | 我用 Cloudflare D1 踩了 5 个坑，第 3 个差点让我放弃 |
| Nuxt Image SSR 问题记录 | Nuxt Image 在 SSR 下为什么会崩，以及三种解法 |

公式：**具体问题 + 有结果/有数字 + 读者视角**

---

## 八、产出节奏

```
日常：L0 持续自动积累（零成本）
随时：挑有价值的发 L1（5 分钟）
信号出现：攒够 3–5 条同主题 → 写 L2（30–60 分钟）
```

按正常编码节奏，**大概 2–3 周出一篇 L2**。
这个频率可持续，也不占太多时间。

**不要给自己定"每周一篇"的硬指标** —— 按信号走，
素材不够时强行凑出来的文章质量一定不合格。
