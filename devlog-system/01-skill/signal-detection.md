# 01 · 信号检测规则

> 决定"这次对话值不值得记"。这是控制噪音的第一道闸门。

---

## 一、五类信号

扫描本次对话，检测是否包含以下任一：

### 1. 报错与修复
用户遇到错误/异常，你提供了解决方案，**且方案经过验证**。

```
✅ 值得记：报错有原文、有明确解法
❌ 不记：只是"应该加个 try-catch"这种泛泛建议
```

### 2. 技术决策
对话中出现"选 A 还是选 B"的讨论，**最终有结论**。

```
✅ 值得记："用 D1 batch 还是重试逻辑 → 选了 batch，因为重试边界情况多"
❌ 不记：没有对比，直接用了某个方案
```

### 3. 新工具 / 库引入
本次对话中首次提到或引入了新的 npm 包、服务、API。

```
✅ 值得记：引入了 @nuxt/image 并说明了为什么
❌ 不记：只是加了个依赖，没有讨论
```

### 4. 性能 / 成本发现
提到了**具体数据**：性能数字、费用变化、优化效果。

```
✅ 值得记："gzip 从 42KB 降到 8.2KB"
❌ 不记："性能变好了"
```

### 5. 踩坑标记
出现以下关键词的段落：
`workaround` `hack` `坑` `限制` `不支持` `注意` `没想到` `居然` `坑爹` `踩坑` `有限制`

```
✅ 值得记：有具体现象 + 处理方式
❌ 不记：只是提到"这里要注意"，没有实质内容
```

---

## 二、判断流程

```
检测到关键词/模式？
   ├─ 否 → 不记录
   └─ 是 → 有具体细节吗？
            ├─ 否（太模糊，如"有个问题"）→ 不记录
            └─ 是 → 符合项目 focus 吗？
                     ├─ 否（且不在通用信号里）→ 不记录
                     ├─ 命中项目 ignore → 不记录
                     └─ 是 → 记录
```

---

## 三、明确不记录的

| 类型 | 例子 |
|---|---|
| 代码补全 | "帮我把这个函数写完" |
| 格式调整 | 缩进、命名、lint 修复 |
| 简单问答 | "这个 API 怎么用" |
| 无结论探索 | 试了几种方法都没成功 |
| 纯闲聊 | 与开发无关 |

---

## 四、细节判定标准

信号必须包含**至少一项**具体信息，否则视为太模糊：

- 报错原文（哪怕是一行关键错误）
- 对比的两个方案及其优劣
- 具体数字（耗时、体积、费用、性能指标）
- 具体的限制条件（如"D1 事务不支持跨 HTTP 请求"）

```
❌ "这里有个性能问题，我优化了"
✅ "N+1 查询导致列表接口 800ms，改成批量查询后 120ms"
```

---

## 五、项目配置的优先级

```
全局五类信号  +  项目 focus  → 并集（都记录）
全局五类信号  -  项目 ignore → 差集（ignore 优先）
```

**ignore 优先级最高** —— 即使命中通用信号，只要命中 ignore 就不记录。

---

## 六、质量优先原则

宁可漏记，不可滥记。

**一条高价值记录（有报错原文 + 解决方案 + 决策理由）**
价值远高于十条"改了个 bug"式的流水。

日志膨胀会直接导致后期聚合时的筛选成本飙升，
所以检测的严格程度要偏高。
